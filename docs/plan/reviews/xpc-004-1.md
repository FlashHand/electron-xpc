## `targetPortId` plumbing

`XpcTask.targetPortId` is optional and set only on `exec()`'s `port` branch
(`xpcCenter.helper.ts:141`). It stays `undefined` for main and renderer targets, so
`task.targetPortId === portId` cannot accidentally match a non-port task — `portId` is always a
non-empty UUID string.

## Findings

| # | Severity | Blocking | Finding |
|---|---|---|---|
| 1 | P2 | non-blocking | `kill()` unregisters *before* `child.kill()`, so an in-flight task settles `null` even if the child would have replied in the same tick. Deliberate: a caller resolving `null` promptly is the contract, and a late reply after unregister is dropped harmlessly because its `pendingTasks` entry is gone |
| 2 | P3 | non-blocking | A task already unblocked by `unregisterPort` is removed from `pendingTasks` by its own `exec()` continuation, not by `unregisterPort`. Correct, but it means `pendingTasks` briefly holds settled tasks — same as every other settle path |
