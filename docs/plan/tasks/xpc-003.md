# xpc-003 — Utility process can send to main, renderer, and other utility processes

## Objective

Route `xpcUtilityProcess.send()` through `xpcCenter.exec()` and reply on the port, so the call
settles. Satisfies R1 and restores invariant 4 for the utility egress path.

Root cause: [../../issues/utility-send-never-resolves.md](../../issues/utility-send-never-resolves.md)

## Context

- [../../architecture/README.md](../../architecture/README.md) — §Routing: `send()`, §Wire protocol
- [../../architecture/utilityProcess.md](../../architecture/utilityProcess.md) — §API `send()`
- [../../issues/utility-send-never-resolves.md](../../issues/utility-send-never-resolves.md)

## Required design

Add the missing `__xpc_exec__` branch to `createUtilityProcess()`'s port listener:

```text
on __xpc_exec__ (payload):
    ret = await xpcCenter.exec(payload.handleName, payload.params)
    port2.postMessage({
      type: __xpc_finish__,
      payload: { ...payload, ret: ret ?? null },
    })
```

`XPC_EXEC` must be added to that file's constant block — it is currently absent, which is why the
omission is easy to miss.

### The id rule

The reply **must** carry `payload.id` — the id minted inside the *utility* process. `xpcCenter.exec()`
mints its own separate id for the downstream leg; replying with that one would never match the
utility's `pendingTasks` entry and would reproduce the original hang. Spell this out in a code
comment: it is the single most breakable detail in this change.

### Coverage that comes for free

`exec()` already dispatches on owner type, so one branch covers all four egress targets plus the
registry miss:

| Target | `exec()` branch | Case |
|---|---|---|
| main | `type === 'main'` → local handler | T1 |
| renderer | `type === 'renderer'` → `webContents.send` | T2 |
| another utility | `type === 'port'` → that port | T3 |
| itself | `type === 'port'` → the same port | T4 |
| unregistered name | `registry.get` miss → `null` | T10 |

T4 (self-send) round-trips two `__xpc_finish__` messages over the same port in opposite directions.
Confirm by reading both sides that the id namespaces keep them apart: main looks ids up only in
`xpcCenter.pendingTasks`, the utility only in its own `pendingTasks`, so a wrong-direction lookup is a
miss and a no-op. Do not add a direction discriminator to the wire — see §Wire protocol asymmetry 2.

## Path

- `src/main/xpcMain.helper.ts`

## Constraints

- Do not rename the main→utility forward type from `'exec'` to `'__xpc_exec__'`. The two spellings
  encode direction on one bidirectional port and both sides already agree.
- `src/utilityProcess/**` needs **no change**. If the implementation appears to require one, stop and
  report — it means the diagnosis in the issue doc is wrong.
- Errors thrown inside `exec()` are already caught there and yield `null`; do not add a second layer
  of try/catch that would swallow a genuine router bug.
