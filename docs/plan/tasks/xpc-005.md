# xpc-005 — Manual Electron harness in `test/`

## Objective

Build a runnable Electron app under `test/`, started by one yarn command, where a human clicks a
button per case and sees main-process, renderer, **and utility-process** output — utility output
surfaced through the main process. Satisfies R6 and is the functional evidence for R1–R4.

## Files

```text
test/
├─ main.js       # xpcCenter.init(), window, forks utility A + B, pipes their stdio, main handlers/subs
├─ preload.js    # requires ../dist/preload → auto-exposes window.xpcRenderer; renderer-side handlers
├─ index.html    # layout + buttons + log pane
├─ renderer.js   # button wiring, renderer handlers/subs, log rendering
└─ utility.js    # both utility processes (behavior varies by --name arg)
```

Plain CommonJS JavaScript, **no build step of its own**. Each file requires the shipped bundle by
relative path (`require('../dist/main')`, `require('../dist/utilityProcess')`), which is what a real
consumer gets from `electron-xpc/main` / `electron-xpc/utilityProcess`. Note the package-specifier
equivalent in a comment at each require site.

`BrowserWindow` config: `contextIsolation: true`, `sandbox: false` (preload must `require`),
`nodeIntegration: false`. `renderer.js` is a plain `<script>` and uses `window.xpcRenderer` only —
never `require` — matching the `electron-xpc/renderer` bridge model.

Two utility processes, forked from the same `utility.js` with `args: ['--name=A']` / `['--name=B']`:

| Process | Owns | Subscribes | Purpose |
|---|---|---|---|
| utility A | `utility/A/echo`, `utility/A/callOut` | `bus/ping` | the sender under test |
| utility B | `utility/B/echo` | `bus/ping` | the *second* peer — makes T3 genuinely cross-process and makes T7 self-exclusion observable |
| utility C | — (owns nothing) | — | forked lazily by T12 to prove a handler-less process can still broadcast |

## Log unification

Three sources must be visible in **two** places (on screen and in the launching terminal), without
feedback loops. One direction per source:

```text
utility A/B ──console.log──► child.stdout ──► main prints "[utility-A] …"  ──┐
main ────────────────────────────────────────► main prints "[main] …"       ├─► xpcMain.broadcast('log/line')
renderer ──xpcRenderer.send('log/append')───► main prints "[renderer] …"   ──┘            │
                                                                                          ▼
                                                            renderer subscribes 'log/line' → on-screen pane
```

- Utility → main is `child.stdout` / `child.stderr` piping (`createUtilityProcess` already sets
  `stdio: 'pipe'`). This is the mechanism R6 names explicitly; do not use an XPC channel for it.
- Renderer → main uses `send('log/append')` so renderer output reaches the terminal.
- Main → renderer uses `broadcast('log/line')` for the on-screen pane. The renderer's own
  `log/append` sends must **not** be re-broadcast back to it as new lines it then re-sends — the
  renderer appends its own lines locally and relays them to main for printing only.

Every line carries a monotonic timestamp and a source tag: `main`, `renderer`, `utility-A`,
`utility-B`, `utility-C`.

```text
├────────────────────────────────────┬─────────────────────────────────────────┤

│                                    │                                         │

├────────────────────────────────────┴─────────────────────────────────────────┤

└──────────────────────────────────────────────────────────────────────────────┘
```

- Case list scrolls independently; log pane owns its own scroll and auto-scrolls to the newest line.
- Results strip is fixed at the bottom: `·` not yet run, `✓` pass, `✗` fail, with the failure reason
  appended to the log.
- Each case button is independently clickable in any order and re-clickable. **Run all** executes
  T1→T12 sequentially and fills the strip.
- T11 disables itself after running (utility B is gone) and states so in the log.

Every button carries a stable `name` attribute (`harness__case__t1`, …) so the layout stays
locatable.

## Assertions

A case is PASS only on an explicit expectation, never on "no exception thrown":

| Case | Assertion |
|---|---|
| T1 | resolved value deep-equals the main handler's return, and the main handler logged that it ran |
| T2 | resolved value equals the renderer handler's return |
| T3 | resolved value identifies **B** as the responder (`{from: 'B'}`), not A |
| T4 | resolved value identifies A as both sender and responder |
| T5 | `xpcMain.send('utility/A/echo')` resolves A's return |
| T6 | `xpcRenderer.send('utility/A/echo')` resolves A's return |
| T7 | main + renderer + **B** each recorded receipt; **A recorded no receipt** |
| T8 | A + B + renderer each recorded receipt; main recorded none |
| T9 | main + A + B each recorded receipt; renderer recorded none |
| T10 | resolves `null` in under 1s |
| T11 | after `kill()`, `send('utility/B/echo')` resolves `null` in under 1s, **and** `send('utility/A/echo')` still resolves normally |
| T12 | a utility process owning zero handlers broadcasts and its message is received |

T7/T8/T9 need receipt collection across processes: each subscriber appends a receipt line, and the
case gates on the collected set after a bounded settle window. State the window in the log rather
than hiding it.

## Scripts

```json
"test:app": "yarn build && electron test/main.js"
```

Build is inside the script so R6's "one command, no manual build step" holds.

Also add a non-interactive mode for agent-side verification:

```json
"test:auto": "yarn build && electron test/main.js --auto"
```

`--auto` creates the window with `show: false`, runs the T1–T12 matrix once the renderer signals
ready, prints the PASS/FAIL table to stdout, and exits with code 0 (all pass) or 1 (any fail). This is
an addition beyond R6's literal wording — it exists so the sprint can be verified without a human in
the loop, and so the harness cannot silently rot. `test:app` remains the human path R6 asks for.

## Path

- `test/main.js`, `test/preload.js`, `test/index.html`, `test/renderer.js`, `test/utility.js`
- `package.json` (scripts only)
- `.npmignore` (add `test/` — the harness must not ship to npm)

## Constraints

- No test framework, no bundler, no TypeScript in `test/`. Zero new dependencies beyond the
  `electron` devDependency from xpc-001.
- The harness consumes `dist/`, never `src/` — it must test what ships.
- No `src/**` changes. If a case cannot pass without one, stop and report: that is a routing bug for
  xpc-002/003/004, not a harness problem.
- Do not launch Electron as part of development. Building the harness and running it are separate
  steps; the run is Ral's call.
